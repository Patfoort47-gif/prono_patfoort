# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

BetMaster / BotPari : application web **statique** (HTML + JS vanilla en module ES, sans framework, sans build, sans dépendance npm) d'aide à la décision pour des paris sportifs **virtuels**. Hébergée sur GitHub Pages. Toute l'interface et les textes sont en français.

## Commandes

```bash
npm start          # python3 -m http.server 4173 → http://localhost:4173
npm test           # node --test (exécute app.test.js, club.test.js, league.test.js, special.test.js, rewards.test.js, auth-model.test.js, community.test.js, shop.test.js et avatar.test.js)
node --test --test-name-pattern="combiné" app.test.js   # un seul test (filtre sur le nom)
node scripts/update-fixtures.mjs   # régénère data/fixtures.json (requiert FOOTBALL_DATA_TOKEN et THE_ODDS_API_KEY, sinon données partielles)
node scripts/update-results.mjs    # met à jour uniquement les scores ESPN (sans clé)
```

Aucun linter ni formateur n'est configuré.

## Architecture

Trois morceaux qui communiquent par le fichier `data/fixtures.json` (et, pour les comptes, les paris et les ligues, par la base Supabase, voir « Club » plus bas) :

1. **Pipeline de données (Node 20, GitHub Actions)**
   - `scripts/update-fixtures.mjs` (workflow `update-fixtures.yml`, uniquement à 7 h, 14 h et 19 h en heure de Paris) : calendriers ESPN (19 compétitions de la liste `leagues` : championnats, coupes d'Europe, coupes nationales et sélections ; J-7 à J+7, conservés J-3 à J+7). Ce workflow n'est déclenché ni par un push ni manuellement : une modification du site ou un rechargement navigateur relit seulement le dernier fichier publié et ne contacte jamais le fournisseur de cotes. Les cotes réelles et la forme ne couvrent que les compétitions de `providerMap`, les autres gardent les cotes du modèle. La liste `leagues` de `scripts/update-results.mjs` et l'objet `LEAGUES` de `app.js` (logo, importance, famille) doivent suivre les mêmes libellés, historique football-data.org pour la forme des équipes (remplace `homeGoals`/`awayGoals` si au moins 2 matchs par équipe), cotes The Odds API (moyenne des bookmakers par marché, avec `bookmakerOffers`, `realOddsMarkets`, `oddsBookmakerCounts`). Toutes les cotes 1N2, BTTS et Over 2,5 sont actualisées ensemble, sans appel nocturne. BTTS et Over 2,5 couvrent les rencontres des prochaines 48 h, interrogent les régions `eu,uk` et conservent la dernière cote réelle de chaque bookmaker lorsqu'une réponse manque ; `odds-cache.js` porte les règles pures de fenêtre, horaires et fusion. Sans cotes réelles, les cotes viennent d'un modèle interne (`model()`). Compare avec le fichier précédent pour calculer `oddsMovement` (significatif à ±5 %), et fige `suggestedPick` une fois le match terminé pour que le pronostic affiché a posteriori soit celui proposé avant le match.
   - `scripts/update-results.mjs` (workflow `update-results.yml`, toutes les heures) : relit `data/fixtures.json`, fusionne les scores ESPN des 4 derniers jours dans `settlements` et marque les `matches` correspondants comme terminés.
   - Les deux workflows commitent `data/fixtures.json` (commits `chore: actualise les …` du bot, d'où des commits fréquents sur `main` : faire `git pull --rebase` avant de pousser) puis redéploient Pages. `pages.yml` redéploie à chaque push sur `main`. Ils partagent le groupe de concurrence `betmaster-pages`.
   - Les identifiants de match sont `espn-<id>` ; le rapprochement des équipes entre fournisseurs passe par `normalize()`/`sameTeam()`.

2. **Front (`app.js`, `index.html`, `styles.css`)**
   - `model.js` contient les calculs purs, sans DOM, importés à la fois par `app.js` et par `scripts/update-fixtures.mjs` (qui s'en sert pour figer `suggestedPick`) : `poisson`, `analyseMatch` (Poisson sur grille 0–8 buts → probabilités 1N2, +2,5 buts, BTTS et `value = proba × cote − 1`), `recommendedMarket`, `optimizeCombo` (recherche exhaustive sur 18 candidats max, profils `safe`/`balanced`/`bold`), `selectionResult`, `settleBet`. Changer la logique de pronostic ici change donc à la fois le site et les pronostics enregistrés par le pipeline.
   - `app.js` est le reste de l'interface : rendu par `innerHTML` à partir d'un objet `state` global, avec `render()` qui redessine tout. Il est écrit en style très compact (une fonction par ligne), tout comme `model.js` : garder ce style en les modifiant.
   - Logos : `scripts/update-fixtures.mjs` enregistre pour chaque match les adresses `homeLogo`, `awayLogo` `leagueLogo` et `leagueLogoDark` renvoyées par l'API ESPN. Le site les charge en direct depuis `a.espncdn.com`, après un contrôle par `safeLogo()`. Pour les compétitions, il prend la version sombre en thème sombre et se rabat sur l'identifiant de `LEAGUES`. Les blasons des clubs n'ont pas de version sombre. Si une image manque ou ne charge pas, il affiche les initiales.
   - Compétitions : la barre horizontale ne montre que celles qui ont des matchs sur la période affichée, triées par importance (`rankedLeagues()`). Le bouton « Compétitions » ouvre la liste complète.
   - Animations : un écran d'accueil s'affiche une fois par session (classe `intro` posée dans le `<head>`), puis la page entre en animation. Tout est coupé si le système demande moins d'animations.
   - Scores en direct : `pollLive()` interroge l'API ESPN depuis le navigateur toutes les 20 s, de 10 min avant à 4 h après le coup d'envoi (champ `kickoff`). Il demande le scoreboard avec la date du match, essaie la veille puis le résumé direct du match en secours. Les cotes sont alors fermées sur la fiche, et un match terminé est réglé tout de suite, sans attendre `update-results.mjs`. Le parsing pur des réponses est dans `live.js`. Le slug ESPN de chaque compétition est le 5e élément de `LEAGUES`.
   - Effets pendant la navigation : fil des matchs (`renderRail`, colonne à gauche dès 1200 px, bandeau collant en dessous), affiche du jour avec compte à rebours, apparition des fiches au défilement (`observeCards`, une seule fois par fiche grâce à `state.revealed`, car `renderMatches()` redessine la liste à chaque changement du ticket), liseré tournant sur les value bets, cote qui s'envole vers le ticket (`flyToTicket`).
   - Fiches détaillées (`details.js`, chargé à la demande par `app.js` comme `account.js`) : fiche équipe (clic sur une équipe : effectif, classements ou parcours en coupe, buteurs, matchs), détail du match (« Plus de détails » : compo, classement, buteurs, infos, et en direct ou après le match les stats et le fil du match) et section Classements (`#classements`). Une fiche ouverte depuis une autre s'empile : les flèches de l'en-tête et le bouton retour du navigateur parcourent cet historique (`stack`, une entrée `history` par fiche, toutes retirées à la fermeture). Tout vient de l'API publique d'ESPN, appelée depuis le navigateur avec un cache de quelques minutes. La compo probable est le dernier onze aligné dans la même compétition, sinon dans n'importe quelle compétition hors amicaux. Les buteurs d'une équipe viennent de la fiche de son prochain match dans la compétition, car le classement général d'ESPN s'arrête au top 50. ESPN ne fournit ni blessures, ni entraîneur en poste, ni buts attendus, et son commentaire détaillé est en anglais. L'équipe type de la fiche équipe reprend, sur les 5 derniers matchs officiels, le schéma le plus fréquent et le titulaire le plus aligné à chaque poste. L'adresse `teams/{id}` d'ESPN refuse les appels du navigateur (pas d'en-tête CORS) : les infos du club (couleur, logo, rang, bilan) viennent de `teams/{id}/roster`.
   - Thèmes : toutes les couleurs sont des variables CSS. Le thème sombre est sur `:root` et le thème clair sur `:root.light`. Utiliser `--accent` pour les aplats et `--accent-text` pour le texte et les traits, car le vert citron n'est pas lisible sur fond clair. Un script dans le `<head>` applique le thème choisi avant le premier affichage.
   - Chargement : cache `localStorage` (`betmaster-fixtures-cache-v2`) appliqué immédiatement, puis `fetch('data/fixtures.json')` toutes les 5 min. Sans données, repli sur `DEFAULT_MATCHES` (démo).
   - État utilisateur : favoris, profil, matchs personnalisés et anciens paris du navigateur (« avant saison 1 ») dans `localStorage` (`betmaster-state-v1`) et, avec un compte, dans `user_states` ; thème dans `betmaster-theme`. Bankroll, paris certifiés, statistiques, ligues, XP et jetons vivent côté serveur (voir « Club » plus bas).
   - Règlement : les paris certifiés sont réglés par le serveur (`settleTicket`, voir « Club ») ; `settlePendingBets` ne règle plus que les anciens paris du navigateur (`state.legacy`) contre `settlements` + matchs terminés. Le rapprochement se fait par `matchId`, sinon par noms d'équipes pour ces anciens paris (les IDs peuvent changer).

3. **Tests (`app.test.js`, `club.test.js`)** : `node:test`. `club.test.js` couvre les règles du Club (règlement serveur, ligues, niveaux, jetons). Les calculs sont testés depuis `model.js`. Un test charge aussi `app.js` après avoir simulé `localStorage`, `location` et `document`, car le module exécute du code DOM au chargement : tout nouvel accès global au DOM ou au navigateur au niveau module doit rester compatible avec ces stubs (ou être protégé par `typeof window !== 'undefined'`).

## Club : comptes, paris certifiés et ligues (lots 8 à 10)

Les paris des joueurs connectés sont **enregistrés et réglés côté serveur** (Supabase). Le navigateur affiche et demande, il n'écrit plus aucune bankroll, aucun statut, aucune statistique.

- Scripts SQL à exécuter dans l'ordre par le propriétaire du projet Supabase (`SUPABASE_SETUP.md`) : `supabase-schema.sql`, `supabase-v3-schema.sql`, `supabase-v4-schema.sql` (annuaire, pseudo unique), `supabase-v5-schema.sql` (tickets certifiés), `supabase-v6-schema.sql` (points de ligue, quota de 10 paris libres par semaine, table `league_entries`), `supabase-v7-schema.sql` (défi du jour), `supabase-v8-schema.sql` (ligue générale), `supabase-v9-schema.sql` (ligues spéciales), `supabase-v10-schema.sql` (XP, trophées, défis hebdomadaires), `supabase-v11-schema.sql` (jetons), `supabase-v12-schema.sql` (club de cœur), `supabase-v13-schema.sql` (profil et confidentialité), `supabase-v14-schema.sql` (ligues privées), `supabase-v15-schema.sql` (hub communauté), `supabase-v16-schema.sql` (boutique), `supabase-v17-schema.sql` (avatar 3D : validation, possession des objets, seau Storage « avatars »). Tous sont réexécutables. `supabase-v5-recette.sql` est la recette de sécurité à jouer à la main.
- Tables `fixtures` (alimentée par le pipeline), `player_accounts`, `capital_events`, `bets`. RLS : lecture par le propriétaire seulement, aucune écriture directe. Écritures par RPC `security definer` : `ensure_player_account`, `add_capital`, `place_bet` (contrôle connexion, coup d'envoi, cotes à 2 % près, mise couverte) et, pour la clé `service_role` seulement, `settle_bet` (idempotent).
- `scripts/sync-supabase.mjs` (étape finale des workflows `update-fixtures.yml` et `update-results.yml`) envoie les matchs dans `fixtures` puis règle les paris en attente avec `settleTicket` de `model.js` (même logique que le site). Rapprochement par identifiant de match uniquement. Un match annulé (`voided`) rembourse la sélection ; un match jamais joué au bout de 10 jours est annulé. `scripts/supabase-admin.mjs` est le client REST `service_role` (sans dépendance npm).
- Côté site, `account.js` expose `placeBet`, `addCapital`, `refreshServer` ; `app.js` garde `state.serverBets` (paris certifiés) et `state.legacy` (anciens paris du navigateur, « avant saison 1 »), et reconstruit `state.history` avec `rebuildHistory()`. Les statistiques publiques viennent de la vue `public_profiles` (calculées depuis `bets`).
- Ligue générale : `leaguePoints` (mise fixe de 10, cote plafonnée à 10), `weekKey` (semaine de Paris), `leagueEligibility` dans `model.js`. Le serveur décide (déclencheur `bets_prepare_league`), le ticket affiche l'interrupteur « Compte en ligue » avec les mêmes règles.
- Défi du jour : `pickDailyChallenge` (model.js) choisit chaque jour (Paris) 4 matchs avec cotes 1N2 réelles (importance de la compétition, puis cotes les plus serrées), figés une fois publiés ; écrit dans `data/fixtures.json` (`dailyChallenge`) par `update-fixtures.mjs` et dans `daily_challenges` par `sync-supabase.mjs`. Pronos par la RPC `play_daily_pick` (avant le coup d'envoi), réglés par `settle_daily_pick` avec le barème de la ligue ; les points entrent dans `league_entries`. Carte `#daily-challenge` en tête de l'onglet Matchs.
- Ligue générale (`league.js`, pur et testé dans `league.test.js`) : 17 échelons (District III à Master), groupes de 10 à 20 en serpentin, saison = mois civil de Paris. `closeSeason` applique montées, descentes, barrages (défis du dernier week-end), placement, montée directe, saison de découverte, inactivité. `scripts/league-engine.mjs` recalcule les classements (`standings`, après chaque règlement via `sync-supabase.mjs`) et prépare la clôture, envoyée en une transaction par la RPC `apply_season_close` ; `close-season.yml` la lance chaque jour à 00 h 30 (idempotent). Le site affiche « Ma ligue » (`#my-league`) et l'écran de fin de saison (`#season-dialog`, une seule fois via `mark_season_seen`).
- Ligues spéciales (`special.js`, pur, testé dans `special.test.js`) : catalogue en base (`special_leagues`, extensible par insertion : compétitions par libellé du site, clubs par identifiant ESPN), sans limite de ligues par joueur, journées calculées par `planRounds` (semaine de Paris, match phare = affiche) et envoyées par `sync-supabase.mjs`. La règle de décision est dans la fonction SQL `special_try_pick` (miroir de `ticketFit`) : un ticket (simple ou combiné) compte dans chaque ligue dont il respecte les règles (déclencheur `bets_attach_special`), la grille de journée est gratuite (`play_special_pick`), quitter supprime les points (un changement par mois). `scripts/special-engine.mjs` règle les pronos de grille, recalcule `special_standings` (saison et mois) et attribue les titres (champion à 60 % des journées, Top 1 % et Top 10 %) via `close-season.mjs`. Le site affiche « Mes ligues », le catalogue, la page d'une ligue (`#special-dialog`) et la liste « Ce pari compte pour » sur le ticket. `settle_bet` renvoie toujours les points : ils servent à la ligue générale (si le ticket compte) et aux ligues spéciales.
- Niveaux, XP et trophées (`xpForLevel`, `levelFromXp`, `titleForLevel`, `streakState` dans `model.js` ; barème, trophées et défis dans `rewards.js` ; tests `rewards.test.js`) : niveaux 1 à 1000 (prestige seul, rien n'est débloqué), XP écrits uniquement par `scripts/xp-engine.mjs` (lancé par `sync-supabase.mjs`) dans `xp_events` avec une clé unique par événement, 12 trophées (`user_badges`), défis hebdomadaires (`challenge_entries`, `challenge_results`, RPC `join_challenge`) qui rapportent de l'XP et des jetons, jamais de points de ligue. Le navigateur n'écrit plus `challengeEntries` ni `challenge_stats`. Le site affiche niveau, titre, barre d'XP (carte profil), niveau dans le classement, panneau des trophées et la notification « +15 XP · prono gagné ».
- Jetons (`piggyBank`, `rankPrize`, `seasonReward`, `featsOf` dans `rewards.js`, tests dans `rewards.test.js`) : monnaie fictive distincte de la bankroll, sans valeur, jamais achetable ni convertible, sans transfert entre joueurs. Journal `token_ledger` (clé unique par joueur, raison et référence : gains idempotents, écrit seulement par `scripts/token-engine.mjs` avec la clé `service_role`), solde par la vue `my_token_balance`. Série et tirelire de saison dans `league_streaks`, détail de fin de saison dans `season_rewards` : (tirelire × régularité + prime de classement) × difficulté + primes d'exploit × difficulté. `close-season.mjs` verse la ligue générale et les ligues spéciales (fin de compétition, primes mensuelles) ; les défis hebdomadaires versent 500, 300 et 150 jetons. Le site affiche le solde (carte profil), la tirelire et la série (Ma ligue) et l'écran « Vos gains » de fin de saison.
- Page « Rejoindre le club » (`#rejoindre`, `join.js` chargé à la demande, règles pures dans `auth-model.js` testées par `auth-model.test.js`) : connexion, inscription en 2 étapes (Identité, Préférences : l'étape Avatar n'existe qu'avec le personnage 3D, aucun avatar simplifié n'est proposé), mot de passe oublié et retour `PASSWORD_RECOVERY`, connexion Google, écran « Vérifiez vos emails » avec renvoi du lien, pseudo vérifié par la RPC `pseudo_disponible`. Toutes les erreurs Supabase passent par `translateAuthError` (aucun message en anglais). `account.js` expose l'objet `auth` ; le menu compte (`#account-menu`, bouton du haut et entrée « Compte » de la barre du bas) remplace l'ancienne fenêtre. Les préférences d'inscription (club de cœur, compétitions, style de jeu) alimentent `favoriteTeams`, `favoriteLeagues` et le profil.
- Page profil (`#profil` et `#joueur-<pseudo>`, `profile.js` chargé à la demande, remplace les anciennes fenêtres de profil et de comparaison) : en-tête (bannière à la couleur de la division, emblème SVG du sprite `#emblems`, niveau, club de cœur), onglets Aperçu, Saisons, Trophées, Mes paris, Avatar et Compte et confidentialité. La carte joueur (6 attributs PRÉ, VAL, RÉG, AUD, VOL, DIS et note sur 99) est calculée par `cardAttributes` et `cardOverall` de `model.js` à partir de la vue `public_player_card` (chiffres bruts publics), provisoire sous 10 paris réglés, partagée en PNG (canvas). Profil public par défaut, détail des paris masqué par défaut (vue `public_bets` : jamais de mise ni de bankroll). Le pseudo ne change que par la RPC `change_nickname` (une fois par mois, le navigateur n'a plus le droit de l'écrire), l'export JSON par `export_my_data`, la suppression par `delete_my_account` (pseudo à saisir, cascades sur toutes les données puis compte d'authentification).
- Ligues privées (`community.js` pour les règles pures, tests `community.test.js`, `supabase-v14-schema.sql`) : code `BM-XXXX`, lien direct `#ligue-privee-BM-XXXX`, sans limite de ligues par joueur, 50 membres par ligue au plus, sans emplacement de ligue spéciale. Tables protégées par RLS (visibles des seuls membres) ; création, adhésion, départ (le propriétaire transmet au plus ancien membre, le dernier ferme la ligue), exclusion, nouveau code et suppression passent par des RPC `security definer`. Le classement (`private_league_ranking`) additionne les points de la ligue générale des membres pour la saison choisie : mêmes pronos, aucun prono en plus ; l'historique est relu dans `league_entries` par saison.
- Hub communauté (onglet Communauté, sections Ma ligue, Général, Suivis, Ligues privées, Challenges, Hall of fame) : le classement Général est paginé côté serveur par les vues `public_ranking_season` et `public_ranking_alltime` (points de la ligue générale, filtres division et club de cœur, recherche par pseudo), avec le podium de la division la plus haute. Suivis : table `follows` (RLS en lecture pour le suiveur, RPC `follow_player` et `unfollow_player`, 200 suivis au plus, profil public requis), nombre d'abonnés par `public_follow_counts`, suggestions (`suggestPlayers` de `community.js` : même échelon, même division, même club de cœur ; profils privés exclus). Fil d'activité : table `activities` écrite par `scripts/activity-engine.mjs` seulement (`planActivities` : combiné gagné à 5,00 ou plus, montée, titre, trophée, palier de niveau tous les 50, arrivée en ligue privée, dépassement), lisible par les abonnés d'un profil public, jamais de bankroll ni de mise. Pastille de nouveauté sur l'onglet Communauté (haut et bas d'écran). Hall of fame : vues `hall_master_champions`, `hall_special_champions`, `hall_fortune`. Comparaison de deux joueurs : bouton Comparer de la page profil (radar superposé et bilan saison par saison).
- Boutique et usages des jetons (`shop.js` pur : catalogue de noms génériques sans marque, raretés et prix validés par les tests, vitrine du jour de 8 objets, objet de la semaine à -30 %, packs stade à -20 %, revente à 30 %, collections, règles de duel ; `shop-page.js` pour l'interface ; `supabase-v16-schema.sql`) : le catalogue est envoyé par `scripts/shop-engine.mjs` (`sync-supabase.mjs`), les achats, reventes, équipements, bouclier de série (800 jetons par saison et par ligue, `streakState(entries, shield)`), recharge de bankroll (500 jetons contre 1 000 € fictifs sous 50 €), duels sur le défi du jour et entrée des ligues premium passent uniquement par des RPC `security definer` qui recalculent le solde sur `token_ledger` sous verrou (aucun achat depuis la console). Les duels sont réglés par `settle_duel` (service_role). Le titre et le cadre de carte s'affichent sur la carte joueur ; maillots, accessoires, trophées, socles, fonds et célébrations s'affichent sur l'avatar 3D (voir « Avatar 3D » plus bas). Les trophées portent les noms des récompenses du football (Ballon d'or, Soulier d'or, Gant d'or, Pichichi, Coupe des champions), choisis par Matteo : noms protégés à valider avant la mise en production (`VALIDATION_JURIDIQUE.md`, question 3). Un badge Collectionneur récompense une collection complète.
- Avatar 3D (BET-49 ; `avatar-config.js` pur et testé par `avatar.test.js`, `avatar-scenes.js`, `avatar-parts.js`, `avatar.js`, `avatar-studio.js`, `avatar-view.js`, `supabase-v17-schema.sql`) : footballeur modélisé par le code (grosse tête expressive, yeux brillants, cheveux en mèches, maillot en maille, matériaux PBR), Three.js 0.170.0 figé depuis jsDelivr, chargé à la demande par le studio, la page profil (aperçu 3D de l'en-tête) et la boutique (cabine d'essayage), jamais sur les autres pages. Éclairage studio (environnement PMREM, lumière principale, deux contre-jours), tons ACES, ombres douces, fond en profondeur de champ aligné sur la ligne de sol commune (`FLOOR_LINE`), qualité haute / moyenne / basse choisie par `qualityFor` (téléphone ou appareil modeste : moyenne), pause hors écran, ressources libérées à la fermeture, « réduire les animations » respecté (pose fixe, pas de rotation). Configuration v2 JSON dans `profiles.avatar_config` (`{v:2, body, skin, face, eyes, expression, hair, hairColor, kit:{item, number, name}, boots, pose, accessories, base, background, showcase, celebration, rev}`), validée à l'identique côté navigateur (`validateAvatar`, `sanitizeAvatar`) et côté SQL (`avatar_config_valid`, contrainte `profiles_avatar_valid`, déclencheur `profiles_check_avatar`) : aucun objet payant sans inventaire (`inventories`) ni déblocage de division (`player_unlocks`), nettoyage automatique à la revente ou à la perte du Master. Anciens avatars (couleur, expression, accessoire) convertis sans perte par `migrateAvatar` (lunettes et casquette offertes par la migration SQL, couronne conservée par un Master seulement). Images : à l'enregistrement le studio rend le buste (512 px) et l'avatar en pied (768 x 1024) avec le fond, WebP (JPEG si le navigateur ne sait pas l'écrire), envoyés dans le seau public Storage `avatars` (`{user_id}/bust` et `{user_id}/full`, écriture réservée au propriétaire par RLS, 1,5 Mo au plus) ; l'adresse se déduit de l'identifiant et de `rev` (`avatarImageUrl`), les classements, le fil, les menus et la carte joueur affichent ces images par `avatarMarkup` (`avatar-view.js`, repli sur l'ancien avatar CSS si l'image manque) sans charger la 3D. Le studio (onglet Avatar du profil) propose Visage, Coiffure, Tenue (numéro et nom au dos), Pose, Accessoires, Socle, Fond (6 fonds unis, centre d'entraînement, vestiaire, tunnel, 6 stades en vue intérieure et extérieure) et Vitrine ; les options verrouillées affichent leur condition (prix en jetons, division requise, objet exclusif) et peuvent être essayées avant achat (non enregistrées tant qu'elles ne sont pas possédées). La boutique a une cabine d'essayage 3D (« Essayer », « Porter ») et l'inscription une étape Avatar (options gratuites). Sans WebGL : l'image enregistrée s'affiche, l'édition est désactivée. Le personnage est une solution de code : il pourra être remplacé par le .glb du graphiste (BET-47) et les fonds par ses rendus (BET-48) sans changer la configuration.
- Cadre légal : la page « Règlement du club » (`#rules-dialog`, lien du pied de page) décrit points, quota, ligues, montées et descentes, ligues spéciales, jetons et boutique ; à tenir à jour avec le code (formules de `model.js`, `league.js`, `special.js`, `rewards.js`, `shop.js`). `VALIDATION_JURIDIQUE.md` liste les cinq questions à faire valider par un juriste (jetons et ANJ, ligues premium, marques et stades, logos ESPN, RGPD) et le suivi des avis : tant que les points 1 à 4 n'ont pas d'avis écrit, les jetons et la boutique ne sont pas à mettre en production.
- Sans connexion au serveur de jeu, aucun pari n'est possible (le bouton l'indique) : il n'existe pas de pari « non certifié ».
